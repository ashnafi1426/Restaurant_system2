# WebSocket Order Status Real-Time Updates

Implementation of WebSocket-based real-time order status updates for the restaurant order tracking system, replacing polling-based status checks with push-based updates via Laravel Reverb.

The change enables guests to receive instant status updates when chefs change order status (pending → preparing → ready → served) without page refresh. The implementation includes channel subscription logic, QR token authentication for guest access, and event broadcasting from the kitchen service.

**Watch for:** Duplicate function declaration breaks the build (confirmed), channels.php allows guest access but BroadcastAuthController requires QR token validation causing potential authorization mismatch (confirmed), reconnection logic re-subscribes but doesn't validate hotel_id is still present (likely).

**Verdict**: CHANGES_REQUESTED

## High-level view

The hotelId empty-string bug is fixed: useOrderStatus now waits for fetchOrderData to complete and extract hotel_id from the API response before calling subscribeToChannel. The fix includes reactive ref updates and localStorage persistence.

The QR token is now sent in the request body (not just headers) when authorizing guest order channels. The BroadcastAuthController validates the token against the order's room/table qr_token field and enforces hotel_id matching for multi-tenant isolation.

OrderStatusUpdated events broadcast to two channels: the customer-specific orders.{hotelId}.{orderId} channel and the hotel-wide hotel.{hotelId}.kitchen channel. The event is dispatched from KitchenService after every status change.

A build-breaking error exists: handlePayNow is declared twice in OrderStatusPage.vue (line 234 and line 335), causing a SyntaxError that prevents compilation.

Channel authorization has a potential gap: channels.php returns true for unauthenticated users on order channels (assuming QR token context validation happens at API level), but BroadcastAuthController enforces QR token validation. If the two don't align, guest subscriptions could fail.

Reconnection cleanup is incomplete: when the WebSocket disconnects and reconnects, the channel is re-subscribed but the code doesn't re-check that hotelId is still valid. If hotelId was somehow cleared from localStorage between disconnect and reconnect, the re-subscription would fail silently.

## QR token authentication for guest channels

The Echo authorizer now includes qr_token in the request body when subscribing to order channels:

```typescript
// echo.ts lines 52-64
const requestBody: any = {
  socket_id: socketId,
  channel_name: channel.name
}

// Include QR token in body for guest authentication
if (qrToken && channel.name.includes('orders.')) {
  requestBody.qr_token = qrToken
  console.log('[Echo] Including QR token in request body for guest order channel')
}
```

BroadcastAuthController validates the token against the order's room/table (lines 109-129), comparing the submitted qr_token against order.room.qr_token and order.table.qr_token. The order is loaded with room and table relationships (line 84: `->with(['room', 'table'])`). Hotel_id validation (lines 96-105) prevents cross-tenant access.

**Concern (likely):** channels.php allows guest access to order channels by returning true when $user is null (line 70: `return true;`). The comment says "we rely on the QR token context validation which happens at the API level before establishing WebSocket connection," but channels.php is called AFTER BroadcastAuthController during the Pusher authorization flow. If channels.php rejects the request, BroadcastAuthController's approval is irrelevant. The two authorization layers should be consistent: either remove the guest=true logic from channels.php (since BroadcastAuthController handles guest validation), or remove the QR token check from BroadcastAuthController and rely solely on channels.php. The current implementation works because channels.php allows guests, but the architecture is confusing.

## Event broadcasting and listener naming

OrderStatusUpdated broadcasts to two channels: orders.{hotelId}.{orderId} (customer-specific) and hotel.{hotelId}.kitchen (hotel-wide), as shown in lines 76-82 of OrderStatusUpdated.php. The event's broadcast name is `OrderStatusUpdated` (line 88). The frontend listens with `.OrderStatusUpdated` (useOrderStatus.ts line 236), which is correct for Laravel Echo.

KitchenService dispatches the event after every status change (startPreparing, markReady, markServed). The event implements ShouldQueue, so it's processed asynchronously by the queue worker.

## Reconnection and cleanup

When the WebSocket disconnects, handleReconnect uses exponential backoff and re-fetches order data before re-subscribing (lines 282-300):

```typescript
setTimeout(async () => {
  await fetchOrderData()
  
  if (hotelId.value && window.Echo.connector?.pusher?.connection?.state === 'connected') {
    console.log('[useOrderStatus] Reconnected - re-subscribing to channel')
    subscribeToChannel()
  } else if (window.Echo.connector?.pusher?.connection?.state !== 'connected') {
    handleReconnect()
  }
}, delay)
```

fetchOrderData refreshes the hotel_id from the API response, so even if localStorage was cleared, the hotel_id reactive ref is repopulated.

**Edge case (possible):** If fetchOrderData fails during reconnection (network error, 403 due to expired QR token), the old hotel_id persists and re-subscription proceeds with stale context. Not blocking but could cause debugging confusion.

Cleanup on unmount leaves the channel (lines 312-318).

## Security: Multi-tenant isolation

BroadcastAuthController validates hotel_id on lines 96-105, rejecting orders where order.hotel_id doesn't match the requested hotelId in the channel name. This prevents a guest from subscribing to orders.{hotelA}.{orderB} where orderB belongs to hotelC.

QR token validation adds a second layer: even if the hotel_id matches, the QR token must match the order's room/table. This prevents guests from one table subscribing to another table's orders within the same hotel.

channels.php also validates hotel_id (lines 48-56).

## STARTUP_GUIDE accuracy

**Inaccuracy (confirmed):** Lines 94-102 state that QUEUE_CONNECTION=sync doesn't require a queue worker. This is misleading. OrderStatusUpdated implements ShouldQueue, which means Laravel will dispatch it to the queue regardless of QUEUE_CONNECTION. With sync, the queue worker is not needed as a separate process because events are processed immediately in the same request, but they still go through the queue system. The guide's phrasing suggests sync mode bypasses the queue entirely, which is incorrect.

The rest of the guide (health check commands, troubleshooting, environment configuration, production deployment) is accurate.
