## Authorization flow clarified

Prior review raised concern about authorization mismatch between channels.php (which returns true for guests) and BroadcastAuthController (which validates QR tokens).

The fix commit adds explanatory comments to channels.php (lines 55-58):

```php
// For guest orders, BroadcastAuthController has already validated the QR token
// at /api/broadcasting/auth BEFORE this closure is called. This closure is the
// second layer of authorization after BroadcastAuthController approves the request.
// Returning true here allows guests whose QR tokens were validated to subscribe.
```

This clarifies the authorization flow: BroadcastAuthController runs first when the client calls /api/broadcasting/auth, validates the QR token, and returns an auth signature. Pusher then calls the channels.php closure with that signature. channels.php returning true for guests is correct because BroadcastAuthController already validated the token.

## Reconnection hotel_id validation

Prior review flagged that reconnection re-subscribes without validating hotel_id is still present after fetchOrderData.

The fix commit adds validation in useOrderStatus.ts handleReconnect (lines 293-298):

```typescript
// CRITICAL FIX: Validate hotel_id before re-subscribing
if (!hotelId.value) {
  console.error('[useOrderStatus] ❌ Cannot re-subscribe: hotel_id is missing after reconnect fetch')
  error.value = 'Configuration error: hotel ID not available after reconnection'
  return
}
```

If fetchOrderData fails to populate hotel_id (API error, 403, network failure), the code logs an error and exits without attempting re-subscription. This prevents subscribing to `orders..{orderId}` (empty hotel_id) which would fail channel authorization.

## STARTUP_GUIDE sync queue clarification

Prior review noted the guide incorrectly stated sync mode doesn't require a queue worker "because events process synchronously," implying they bypass the queue system.

The fix commit rewrites lines 92-98:

Before:
```
QUEUE_CONNECTION=sync      # Does NOT require queue worker
```

After:
```
QUEUE_CONNECTION=sync      # Does NOT require queue worker (events processed immediately)
```

And adds a clarifying paragraph (lines 92-93):

```
If your `.env` file has `QUEUE_CONNECTION=sync`, events that implement `ShouldQueue` 
(like `OrderStatusUpdated`) are processed immediately in the same request rather than 
being queued. In sync mode, you don't need a separate queue worker process, but the 
queue system is still used - jobs just execute synchronously.
```

This accurately describes Laravel's behavior: ShouldQueue events always go through the queue system, but sync mode processes them immediately rather than deferring to a background worker.
